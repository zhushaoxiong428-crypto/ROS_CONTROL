# 直线起步标定与验证

## 问题与基线

车辆收到相同左右轮目标时，右轮会比左轮更早加速，因此产生正角速度并向左偏。历史串口日志中有两次目标为 `29.38 rpm`（约 `100 mm/s`）的直线阶跃：

| 指标 | Run 1 | Run 2 |
| --- | ---: | ---: |
| 左/右轮达到 10% 目标 | 120 / 80 ms | 100 / 80 ms |
| 左/右轮达到 90% 目标 | 240 / 200 ms | 240 / 200 ms |
| 前 500 ms 峰值轮速差 | 6.81 rpm | 4.72 rpm |
| 前 1 s 平均 `右-左` | 1.85 rpm | 1.79 rpm |
| 前 1 s 积分轮程差 | 6.41 mm | 6.17 mm |
| 按 131.7 mm 轮距预测偏航 | 2.79° | 2.68° |
| 最后 5 s 左/右平均转速 | 29.22 / 29.50 rpm | 29.30 / 29.39 rpm |

稳态差只有 `0.09~0.28 rpm`，问题主要发生在起步后的约 `400 ms`，因此不能直接把稳态所需的左右 PWM 强制改成相同值。

根因是现有前馈来自悬空稳态实验，最低标定点为 `14.69 rpm`，但目标斜坡从低转速开始。原模型在首个控制周期会给左、右轮约 `122/136 PWM`，把未标定的低速静摩擦区当成了稳态线性区。

### 当前低速基线（2026-09-24）

在 320 点 `/scan`、Best Effort 遥测固件上又完成了三次相同的架空实验：`0.05 m/s` 前进 `1.5 s`，随后连续发送零速 `2 s`，命令频率 `20 Hz`。三次都由操作者确认两轮向前、无异响和抖动，`startup_fault=0`，停车目标和 PWM 均在 `500 ms` 看门狗期限内归零。最低电压依次为 `7.558/7.535/7.512 V`。

## 控制结构

独立轮速 PI 和左右稳态前馈仍是基础控制量。直行时附加轮间同步误差：

```text
e_sync = (target_left - actual_left) - (target_right - actual_right)
trim   = Kp_sync * e_sync + Ki_sync * integral(e_sync)

pwm_left  = base_left  + trim
pwm_right = base_right - trim
```

正向直行且右轮更快时，`e_sync > 0`，控制器增加左轮输出并减小右轮输出；该符号关系在反向直行时同样成立。

起步状态机只在以下条件全部满足时启用：

- 速度控制模式；
- 指令为直线运动，左右最终目标同号且相差不超过 `0.5 rpm`；
- 最终目标绝对值不低于 `14 rpm`；
- 两个编码器均已初始化；
- 目标斜坡已经进入最终指令方向。

状态机行为：

1. 两轮都未起转时，分别保证至少达到起步 PWM。
2. 只有一轮达到正确方向的 `1 rpm` 时，未起转轮继续获得托底，已起转轮不允许超过其起步 PWM，避免快轮继续拉开距离。
3. 对“从静止开始的正向直线起步”，两轮同时达到阈值后不再硬切换：以已经验证安全的 `145/145 PWM` 为释放起点，在 `300 ms` 内线性混合到每一拍实时计算的正常前馈与同步修正输出。第一拍仍是 `145/145`，第 15 个 20 ms 间隔结束时完全回到原控制量。
4. 释放期间冻结同步积分，且起步超时不再计时；这避免已经成功起转后因释放时间误报故障。释放结束后稳态前馈、轮速 PI 和同步 PI 参数完全不变。
5. 只有初始两轮均低于 `1 rpm` 的正向静止起步会武装平滑释放；滚动调速、转弯、停车、反向起步和正反换向保持原行为。任何不再满足直线条件的命令都会立即取消释放状态。
6. `300 ms` 内未完成起步时锁存故障并制动；零速度指令会清除故障。
7. 换向时先让目标经过一个零速控制周期并复位轮速 PI；若车轮仍沿旧方向转动，先以零 PWM 滑行至接近静止，再允许反向起步。

每侧释放公式为：

```text
alpha = clamp(release_elapsed / 0.30, 0, 1)
pwm   = (1 - alpha) * 145 + alpha * pwm_normal
```

当前 `/motor_debug` 中的 `startup_active=1` 同时覆盖起转辅助和线性释放阶段，尚没有单独的 `release_active` 遥测字段；判断释放形状时应同时查看最终 PWM。

## 默认参数

| 参数 | 默认值 | 说明 |
| --- | ---: | --- |
| 左/右起步 PWM | 145 / 145 | 来自两次现有起步日志的初始实验值 |
| 起转阈值 | 1 rpm | 必须与命令方向一致 |
| 起步超时 | 0.30 s | 超时制动并锁存故障 |
| 正向起步释放时间 | 0.30 s | 仅静止正向直行；从等 PWM 线性过渡到正常输出 |
| 同步误差死区 | 0.5 rpm | 抑制编码器量化噪声 |
| `Kp_sync` | 0.25 PWM/rpm | 保守初值 |
| `Ki_sync` | 0.50 PWM/(rpm·s) | 起步阶段冻结积分 |
| 同步修正限幅 | ±8 PWM | 同时受两侧实际 PWM 余量限制 |
| 默认轮速 PI | `Kp=1.2, Ki=0.5, Kd=0` | 与历史实测时 NVS 参数一致 |

起步与同步初值主要依据历史 `29.38 rpm` 实验，释放候选依据上述三次 `14.69 rpm` 架空基线；它们都不能替代不同电压、载荷、地面和反向运动下的实车标定。尤其不能假设反向静摩擦与正向相同。

### 300 ms 平滑释放的首轮 A/B 验证

本候选只改变上述硬切换，不调整左右稳态前馈、轮速 PI、同步 PI、目标斜坡、通信 QoS 或 `/scan`。构建产物 `build/leap_low_v1.bin` 的 SHA-256 为 `75ace2c7b251e515c645cc5ac55ead928922744a999ab61156ce54484f62eeec`；烧录后应使用可追溯标签 `startup_release_300ms_75ace2c7`。在保持车轮架空并再次确认安全后，三次实验分别使用新目录：

```bash
python3 tools/run_motor_startup_trial.py data/trial_startup_release_300ms_01 \
  --firmware-id startup_release_300ms_75ace2c7 \
  --speed-mps 0.05 --drive-seconds 1.5 --zero-seconds 2 --rate-hz 20 \
  --wheels-suspended
```

后两次只把目录末尾改为 `_02`、`_03`。每次之间必须确认电机已经停止，仍需记录实际旋转方向、异响和抖动。该阶段的预注册判据不是最终的 `20 ms` 目标，而是验证根因假设：三次均无起步故障，右轮 t90 领先由基线的 `420~480 ms` 降到不超过约 `250 ms`，前 500 ms 可见峰值差由 `≥4.995~5.808 rpm` 降到不超过约 `4 rpm`，且不能反转成明显的左轮领先。若仍超过 `300 ms` 或 `4 rpm`，说明硬切换不是主要原因或 `300 ms` 释放仍太快；若反转为左轮领先超过 `3 rpm`，应先把释放缩短到 `200 ms`，不能同时修改 PI 或前馈。

2026-09-24 已完成三次候选固件架空试验，操作者均确认两轮向前、无异响、无抖动、无突然加速并正常停车；三次 `startup_fault=0`，目标/PWM 分别在最后一条非零命令后约 `92.6/88.5/84.7 ms` 归零：

| 试验 | 运动最低电压 | 左/右 t90 | 右轮领先候选 | 前 500 ms `|R-L|` | 证据等级 |
| --- | ---: | ---: | ---: | ---: | --- |
| `_01` | `7.405 V` | `960~980 / 240~440 ms` | `520~740 ms` | `≥2.706 rpm` | 缺帧较多，仅候选/下界 |
| `_02` | `8.040 V` | `280 / 240~260 ms` | `20~40 ms` | `≥2.053 rpm` | 少量缺帧，仅候选/下界 |
| `_03` | `8.030 V` | `260 / 260 ms` | `0 ms` | `1.962 rpm` | t90 与前 500 ms 为严格完整窗口 |

`_02/_03` 在约 `8.0 V` 下重复把旧版 `420~480 ms` 的右轮领先降到 `0~40 ms`，并把早期轮速差降到约 `2 rpm`；PWM 也从 `145/145` 逐拍展开，未再出现旧版单周期暴露约 `12~15 PWM` 差值的硬切换。因此候选通过首轮筛选，证明 300 ms 释放方向有效。它仍不是最终全工况验收：旧基线电压为 `7.512~7.558 V`，与两次最佳候选不匹配；低电压 `_01` 的 t90 表现较差；`_03` 的 `1.962 rpm` 仍高于 `14.69 rpm` 目标的 10%（约 `1.47 rpm`）；并且尚未完成落地偏航测试。下一步必须做电压匹配的 A/B 和电压相关前馈标定，不能把改善全部归因于单一算法。

## 采集新数据

先把车轮稳固架空、清空轮边线缆并备好硬件断电手段，确认 micro-ROS agent 已连通，且没有遥控器、导航或其他节点同时发布 `/cmd_vel`。推荐使用单进程试验工具；它会实际发送运动指令，所以不可用于未确认安全的落地测试：

```bash
python3 tools/run_motor_startup_trial.py data/trial_A_01 \
  --firmware-id timing_instrumented_v1 --wheels-suspended
```

工具先确认电机静止、**19 字段新固件遥测**正常、`/cmd_vel` 有订阅者，并要求固定 2S 电池读数在 `[6.4, 8.5] V` 内连续保持至少 `1 s`；消息超过 `1 s` 未更新或 `/battery_state.present=false` 时也不允许运动。每次发送非零命令前和处理回调后都会复查电压、遥测和发布者状态；运动中出现非有限值、超出该试验区间或 MCU 报告样本无效/陈旧时，会立即中止并进入零速阶段。主机预检通过后先发送 `300 ms` 全零命令，重新武装 MCU 电池互锁，再开始正式运动；这些命令在 `events.csv` 中标为 `interlock_rearm`，不计入正式停车延迟。MCU 侧同时要求 3 个不同序号、位于 `6.4–8.5 V` 的样本，并在低压、过压、ADC 无效或样本陈旧时独立制动，详见 [电池运动互锁](power_motion_interlock.md)。`/battery_state` 约每 `100 ms` 可能重复发布电池任务每 `500 ms` 才更新的缓存值，所以主机“连续 1 s”仍只是第二道保守门禁，独立 ADC 样本判定由 MCU 完成。

默认试验随后以 `10 Hz` 发送 `0.10 m/s` 直线指令 `3 s`，然后**立即**以 `10 Hz` 连续发送零速 `1 s`，不在两段之间等待看门狗。未刷入新增 MCU 计时字段的旧固件只有 13 字段，试验脚本会拒绝运行。它会因遥测丢失、启动故障、反向轮速、超速或轮速差过大而提前停止并尽力发送零速。只有运动目标确已生效、零速发出后收到双轮目标/PWM 归零的新遥测、随后滤波轮速低于 `1 rpm`，且**目标/PWM 归零**的观察发生在最后一条非零发送后 `400 ms` 内，才标记为完成。`400 ms` 并非车轮实际停转时间；这个时序只与主动零速停车**相符**，不是 MCU 收到指令的确认。网络异常下零速不能保证送达，固件 `500 ms` 看门狗和操作员硬件断电手段仍不可省略。输出目录必须不存在，以免覆盖旧数据。

`motor_debug.csv`、`events.csv` 和 `metadata.json` 中的主机事件时间共用同一个单调时钟起点。前者记录轮速、PWM、控制内部状态、MCU 控制/发布时刻和最近一次电压；后者记录每次 `/cmd_vel` 的主机 `publish()` 返回时间和每次 `/battery_state` 的主机接收时间。元数据汇总起步前电压、运动期间收到的最低电压及停车后电压。主机发送时间**不是 MCU 收到命令的时刻**；电池 ADC 约每 `500 ms` 取样，ROS 每 `100 ms` 可能重发旧值。MCU 时间戳与主机时间戳没有共同原点，不能直接相减求单程延迟。`metadata.json` 的 `completed` 只说明运动和停车检查通过，不代表采样完整或起步指标达标；完成后仍须分析并检查验收门限：

```bash
python3 tools/analyze_motor_startup.py data/trial_A_01/motor_debug.csv
python3 tools/analyze_motor_startup.py data/trial_A_01/motor_debug.csv --check
```

仅被动观察、不自动发送运动指令时，仍可使用 `python3 tools/record_motor_debug.py data/passive_motor_debug.csv`。该工具兼容旧固件 13 字段和新固件 19 字段；旧数据的新增计时列留空，不会补造时间戳，也不会覆盖已有 CSV。

### MCU 采样链路诊断

`/motor_debug` 原有第 0～12 项不变，新固件追加 6 项：`control_seq_mod65536`、控制快照 MCU 毫秒时间的高/低 16 位、`publish_seq_mod65536`、发布尝试 MCU 毫秒时间的高/低 16 位。控制序号在 `motion_task` 每次形成快照时递增，发布序号在 micro-ROS 每次准备调用 `rcl_publish` 时递增；后者**不是发送成功或主机收到的确认**。两段 16 位数在 `float32` 内可精确表示，组合后按 32 位毫秒计时器处理回绕。

新记录可用 `python3 tools/analyze_motor_timing.py data/trial_A_01/motor_debug.csv` 检查控制快照、发布尝试和主机接收三段间隔。控制序号连续但 MCU 控制时间跨度异常，提示控制任务间隔异常；发布序号连续而控制序号跳变，提示发布任务未观察到中间快照（单槽队列可能已覆盖）；发布序号跳变，说明部分发布尝试没有出现在主机记录中，**不能**单凭这一点断言 Wi-Fi 丢包，因为 `rcl_publish` 也可能失败。主机时间与 MCU 发布间隔不一致可提示传输或接收端排队，但两时钟没有共同原点，不能直接计算绝对单程延迟。旧 13 字段 CSV 仍可用于起步分析，不能用于本项链路定位。

### micro-ROS 发布耗时定位

若 19 字段记录显示 MCU 控制任务仍按 `20 ms` 运行、但发布尝试之间出现长空档，可刷入带发布耗时探针的新固件，保持车轮静止，串口监视至少 `20 s`。探针不改变轮速控制、话题或 QoS；只在 RAM 中累积耗时，每约 `10 s` 输出 `MICROROS_TIMING` 和 `MICROROS_TIMING_PUB` 两行摘要；超过 `50 ms` 的阶段另有 `MICROROS_TIMING_SLOW`，标注最大耗时发生的 MCU 毫秒时刻和 `/motor_debug` 发布序号，以便对照 CSV。不要为诊断同时打开两个占用 `/dev/ttyUSB0` 的串口监视器。

`MICROROS_TIMING` 的 `*_max_us` 分别列出整轮循环间隔 `loop`、`spin_once`、`rcl_wait`、命令处理 `cmd`、定时器回调 `timer`、服务处理 `svc`、取 ROS 时间 `epoch`、运行期 `ping`、建链 `setup_ping` 和上一次报告自身 `report` 的最大墙钟耗时；`*_gt50` 是超过 50 ms 的次数，`timer_count` 与 `debug_count` 可用来判断定时器触发后是否真的发布了调试消息。`MICROROS_TIMING_PUB` 中 `odom/imu/debug/scan/battery/ultra` 各自按 `调用次数/最大微秒/超过 50 ms 次数/失败次数` 输出，**只测实际发生的 `rcl_publish` 调用**，缺数据而跳过发布不计为零耗时。`session` 每次成功建链递增；跨会话、Agent 重连和报告本身导致的间隔须单独看待。

若某项 `rcl_publish` 或 `ping` 的最大耗时与 `/motor_debug` 的长空档同量级，就先排查该路径；若 `timer` 很慢但各发布调用不慢，再查消息准备和时间同步；若 `loop` 很慢而已测阶段都短，再查任务调度/未覆盖路径。耗时是**测量区间内的墙钟时间**，可能包含 FreeRTOS 抢占，不能单独证明某函数内部阻塞。嵌套阶段可能测到同一次停顿，最大耗时不能相加；`MICROROS_TIMING_SLOW` 的 `debug_seq` 是该阶段结束时最新的调试发布序号，不一定属于该阶段本身。该探针已在静止状态记录到发布长耗时，但在运动试验前仍应确认数据链路稳定。

### 遥测发布 QoS A/B 实验

静止实测中，`/odom`、`/motor_debug` 的 `rcl_publish` 墙钟耗时反复达到数百毫秒，而同任务里的 IMU、电池、超声发布没有同样的长耗时。前两者及 `/scan` 使用默认发布 QoS，其余三个话题使用传感器 QoS。这只是关联，尚未证明可靠性就是阻塞根因，也不能把包含任务抢占的墙钟耗时直接等同于函数内部等待。

固件提供 `Leap low settings → Use best-effort reliability for odom, motor debug and scan (A/B test)` 编译开关。关闭为 A 组（默认 QoS），打开为 B 组（仅把这三个发布者的 `qos.reliability` 改成 Best Effort，保持深度等其余 QoS 参数原样）。本次实验已在 `sdkconfig` 打开 B 组开关；后续可用 `idf.py menuconfig` 切换。每次切换后执行 `idf.py build`、`idf.py -p /dev/ttyUSB0 flash monitor`（串口名以实际设备为准），并通过启动日志的 `telemetry_qos=default` 或 `telemetry_qos=best_effort` 确认实际运行组别。`/cmd_vel`、服务、控制器和其他发布者不随此开关改变。

先保持车轮静止、Agent 与 Wi-Fi 条件不变，不运行会发 `/cmd_vel` 的起步试验脚本。每组启动后略过建链初期窗口，再记录至少三个完整的 `MICROROS_TIMING` / `MICROROS_TIMING_PUB` 约 10 秒窗口，核对 `session` 未变化、各 `fail=0`。用 `timer_count * 1000 / window_ms` 算实际发布定时器频率，比较 `odom/debug/scan` 的 `gt50` 和 `max_us`。配置目标为 20 ms 定时器、约 50 Hz；若 B 组恢复到至少约 45 Hz 且长耗时显著减少，说明改变可靠性有帮助，但仍需复测 A 组及核对接收端和数据丢失。若 B 组仍慢，就不能把瓶颈单独归因于 QoS。

现有 A 组日志 `build/log/idf_py_stdout_output_72754` 中选取的连续三个完整窗口共 410 次定时器调用、30.55 秒，约 13.4 Hz；`odom/debug` 分别有 52/46 次超过 50 ms，可作初步参考。严格比较时应使用相同的 ROS 订阅者和环境条件重新采一组 A；最后可按 A→B→A 顺序复测，检查改善能否随开关重复出现。

Best Effort 发布者与要求 Reliable 的订阅者不兼容；切换 B 组后，导航或其他现有 `/odom`、`/scan` 订阅可能停止收到消息，因此 B 组仅用于静止诊断，不能直接当作最终部署配置。仓库的两个 `/motor_debug` 采集脚本已改为显式 Best Effort 订阅，能同时接收 A/B 两组。命令行查看时用 `ros2 topic echo /motor_debug --qos-reliability best_effort --once`；默认可靠订阅的 `echo` 在 B 组可能收不到消息。`fail=0` 也不证明主机收到所有消息，须核对接收端；尤其 `/scan` 消息较大，应单独确认它还能被收到。待通信链路和订阅兼容性验证后，再考虑架空轮的运动试验。

手机热点静止测试还提供 `Leap low settings → Disable LaserScan publication (network A/B test only)` 单变量开关。打开后仍创建 `/scan` publisher，但跳过 `publish_scan()`，启动日志显示 `scan_publish=disabled_ab_test`，时序摘要中的 `scan` 调用数应为 `0`。该开关不改变 `/cmd_vel`、电机控制、看门狗、其他话题频率或 QoS；它只用于判断约 1500 字节的 LaserScan 数据报及其 IP 分片是否造成热点上行拥塞。诊断固件不能用于正常导航，实验结束后必须关闭并恢复 `/scan`。

该 A/B 在同一手机热点上把 `/motor_debug` 主机可见率从 `51.95%` 提升到三次重复的 `93.94%～95.40%`，MCU 控制保持 `50.000 Hz`，因此 `/scan` 大报文是主要干扰因素。生产配置重新启用 `/scan`，并用 `MICROROS_SCAN_POINT_COUNT=320` 将 360 个一度原始桶合并为 320 个约 `1.125°` 的桶；同一输出桶有多个有效点时保留最小距离，避免下采样漏掉近障碍。ROS 2 本机序列化实测由 360 点的 `1504 B` 降到 320 点的 `1344 B`，为 XRCE 头保留空间并避免超过常见的 1500-byte IP MTU。

2026-09-23 在同一手机热点完成 320 点候选验收：实机消息长度为 320，`angle_increment=0.019634955`、`angle_max=6.263550758`；三组 60 秒静止记录的 `/motor_debug` 主机可见率分别为 `94.61%`、`94.04%`、`94.55%`，平均 `94.40%`，接收频率平均 `45.66 Hz`，MCU 控制均为 `50.000 Hz`。结果与关闭 `/scan` 时平均 `94.44%` 基本相同，并显著优于 360 点时的 `51.95%`。连续八个串口统计窗口共约 `80.074 s`，`session=2` 未变化，`scan=770`（约 `9.62 Hz`），扫描发布最大耗时 `2854 us`，全部 `gt50=0/fail=0`；其他发布项也均 `fail=0`。12 秒抓包未发现来自小车的 IPv4 分片。主动停止 Agent 后，重启约 `2.36 s` 建立会话、约 `3.03 s` 完成全部 ROS 实体恢复。主机到达时间仍有 `479～633 ms` 的偶发空档，说明手机热点仍会批量交付数据；运动分析必须使用消息内的 MCU 序号/时间，不能把主机接收时间当作控制时间。

分析脚本只对完整的前 `500 ms`、前 `1 s` 和目标达到平台后的末 `1 s` 计算相应指标；窗口不足或采样中断时显示 `N/A` 且验收不通过，不再把短时或缺失数据当作完整试验。与历史日志做 A/B 时应保持控制斜坡、PI、前馈、命令时序与电压可比；历史目标斜坡约 `200 rpm/s`，当前默认 `100 rpm/s`，不能直接把指标变化归因于同步算法。

建议每个工况重复至少 10 次，并记录 `/cmd_vel`、`/imu`、`/odom` 和 `/battery_state` 作为交叉验证。测试矩阵至少包含：

- `0.1/0.2/0.3 m/s` 前进；
- 单独标定的反向工况；
- 满电、标称电压和低电压；
- 标准载荷和最大设计载荷；
- 停车后再启动与正反换向。

## 最终落地验收门限

以 `29.38 rpm` 直线阶跃为首轮目标：

- 左右轮 90% 上升时间差不超过 `20 ms`；
- 前 `500 ms` 峰值轮速差不超过目标的 `10%`，即约 `3 rpm`；
- 前 `1 s` 编码器预测偏航不超过 `1.5°`；
- 两轮在 `500 ms` 内进入目标 ±5% 并保持 `200 ms`；
- 稳态平均轮速差不超过目标的 `3%`；
- 稳态轮速差 P95 不超过目标的 `5%`；
- 单轮稳态 RMSE 不超过 `1 rpm`。

## 首轮实车安全检查

先架空或使用滚筒确认两侧编码器方向和故障制动，再进行清空场地的短时落地测试。保持与基线实验相同的电池电压，并准备立即发送零速度或断电。

遇到下列任一情况应停止测试并先排查机械、编码器或接线：

- 一轮输出已达到起步 PWM，但 `150 ms` 后仍低于 `1 rpm`；
- 一轮超过 `5 rpm`，另一轮低于 `1 rpm`，持续两个控制周期；
- 轮速差超过 `10 rpm`，或实际转速与命令方向相反；
- 同步修正连续达到 `±8 PWM`；
- 任一轮超过目标的 1.5 倍、出现明显打滑、异响、过流、压降或发热；
- 直行 1 秒偏航超过 `5°`。

若仍向左偏，先比较 `startup_active` 期间的左右轮速和最终 PWM，再以 `2 PWM` 为小步调整左右起步值；若偏差反向，不应继续增大慢侧补偿。交叉 PI 用于处理剩余扰动，不应用来掩盖明显错误的静摩擦前馈。
