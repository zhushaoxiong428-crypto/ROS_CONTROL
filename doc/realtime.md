# 实时性：任务、CPU、内存和话题发布

本文记录固件运行时的资源占用和时序：各任务的优先级、CPU 占用和栈余量，两个核的负载，堆内存，控制循环周期，以及 ROS 话题在电脑端实际收到的频率。测量过程中发现并修复了 micro-ROS 话题漏发的问题。原始数据在 [data/rt_analysis_20261025](../data/rt_analysis_20261025)。

## 测量方法

- **固件内统计**：`rt_stats` 任务（[main/tasks/diag/rt_stats_task.cpp](../main/tasks/diag/rt_stats_task.cpp)）每 10 秒用两次 `uxTaskGetSystemState()` 快照的差值，算出每个任务的 CPU 占用，并通过串口打印。
  - CPU 占用以“单个核的百分比”表示：一个任务独占一个核 10 秒，记为 100%。
  - 核负载 = 100% − 该核空闲任务（IDLE0 / IDLE1）的占比。
  - 栈余量是任务启动以来的最低剩余量（high water mark）。
  - 需要打开 FreeRTOS 的 trace facility 和 run-time stats，计时源是 `esp_timer`。`rt_stats` 自身约占 0.8% CPU，主要花在打印上。
- **控制周期**：运动任务每 500 个周期（10 秒）打印一次周期均值、标准差、最大抖动、执行时间和超时次数（周期 > 22 ms 记为超时）。
- **话题频率**：[tools/topic_rates.py](../tools/topic_rates.py) 在电脑上订阅各话题，统计频率和到达间隔。这是包含 Wi-Fi 和 Agent 延迟在内的端到端数据。
- **测量条件**：插着 USB 读串口，轮子架空；先静止 60 秒，再跑 40 秒速度阶跃（±0.1、±0.2、±0.3 m/s）。FreeRTOS tick 为 100 Hz。这次没有记录电池电压。

## 任务和栈余量

下表来自修复后的一个静止 10 秒窗口（`serial_after_fix.txt`）。“核”是任务的绑定情况，`any` 表示没有绑定，可以在两个核上运行。

| 任务 | 优先级 | 核 | CPU（单核 %） | 栈分配 | 最低剩余 | 已用 |
| --- | --- | --- | --- | --- | --- | --- |
| `microros` | 4 | 0 | 28.25 | 12288 B | 7220 B | 41 % |
| `wifi`（IDF） | 23 | 0 | 6.38 | — | 3444 B | — |
| `tiT`（lwIP） | 18 | any | 5.63 | — | 1888 B | — |
| `imu` | 5 | 1 | 3.69 | 4096 B | 2720 B | 34 % |
| `lidar` | 4 | 1 | 2.13 | 8192 B | 5380 B | 34 % |
| `motion` | 5 | 0 | 1.97 | 4096 B | **1136 B** | **72 %** |
| `rt_stats` | 1 | 1 | 0.76 | 4096 B | 1548 B | 62 % |
| `gamepad_i2c` | 4 | any | 0.60 | 4096 B | 2940 B | 28 % |
| `battery` | 4 | 0 | 0.27 | 4096 B | 1976 B | 52 % |
| `peripheral` | 3 | 0 | 0.14 | 4096 B | 1972 B | 52 % |
| `ultrasonic` | 4 | 1 | 0.13 | 4096 B | 3276 B | 20 % |
| `camera_task` | 3 | any | 0.02 | 4096 B | 1932 B | 53 % |
| `httpd`（配置网页） | 5 | any | 0.00 | — | 11076 B | — |

IDF 的系统任务 `esp_timer`、`sys_evt`、`ipc0` / `ipc1`、`Tmr Svc` 合计 CPU 占用不到 0.1%。

- **优先级的安排**：`motion` 和 `imu` 是优先级最高的应用任务（5）；传感器任务和 `microros` 是 4；外设任务是 3。所以通信任务再忙，也抢不走控制任务的 CPU。比它们优先级更高的只有 IDF 的 Wi-Fi（23）和 lwIP（18）。控制循环约 1 ms 的唤醒抖动，主要就来自这两个任务。
- **栈**：应用任务里余量最小的是 `motion`，最低还剩 1136 B。`microros` 分配了 12 KB，最多只用了约 5 KB，还可以缩小。
- **为什么没绑核的任务也显示在固定的核上**：这些任务都是用 `xTaskCreate`（不绑核）创建的，但 ESP-IDF 会把用到浮点运算的任务，自动绑到它第一次使用 FPU 时所在的核上，因为 FPU 寄存器没法跨核保存和恢复。`imu`、`motion`、`microros`、`lidar` 等都用到了浮点数，所以分别被绑到了 0 号核或 1 号核；`gamepad_i2c`、`camera_task` 没用浮点数，仍然是 `any`。

## 核负载和内存

| | 0 号核 | 1 号核 | 堆剩余（最低） |
| --- | --- | --- | --- |
| 静止 | 42.4–43.2 % | 6.8–7.1 % | 46–47 KiB（36 KiB） |
| 速度阶跃 | 45.1–45.7 % | 7.6–7.7 % | 47–48 KiB（36 KiB） |

两个核负载不均衡：`microros`、Wi-Fi 和 lwIP 都在 0 号核上，加起来约 40%；1 号核基本空闲。堆一共 237 KiB，开机以来最低只剩过 36 KiB。

## 控制循环

修复后静止和运动期间的 11 个 10 秒窗口：周期均值 20.000 ms，标准差 0.07–0.18 ms，最大抖动 0.58–1.38 ms，每周期执行时间平均 0.35–0.43 ms、最长 1.39 ms，超时次数为 0。只有开机后第一个窗口有 7 次超时、最长 59.6 ms（修复前的日志中可以看到），那是 Wi-Fi 连接和 micro-ROS 会话建立期间的一次性开销。

## 话题漏发：现象、排查和修复

**现象**：`/odom` 应该是 50 Hz（20 ms 的 rcl 定时器），实测只有 34 Hz；`/battery_state` 和 `/ultrasonic` 应该是 10 Hz，实测只有 6.8 Hz。所有话题按相同比例下降，说明是 micro-ROS 的发布循环本身变慢了。`/odom` 的到达间隔集中在 20 ms 和 40 ms 两处，中间很少：这说明整个发布周期被跳过了，而不是周期均匀地变长。

**排查**：问题是在加入 `rt_stats` 之后出现的，于是在车上逐一排除（`/odom` 频率，各测 20–60 秒）：

| 条件 | `/odom` |
| --- | --- |
| 打开统计选项，但不运行 `rt_stats` 任务 | 49.9 Hz |
| 运行 `rt_stats`，但它占着同样的内存什么都不做 | 48.3 Hz |
| `rt_stats` 正常运行 | 34.0–34.1 Hz |
| `rt_stats` 正常运行，并且把每轮等待改为 5 ms（修复后） | 49.7–50.0 Hz |

**原因**：发布循环每轮最多等待 20 ms，正好等于发布周期，而 FreeRTOS 的等待又按 10 ms 的 tick 取整。于是一轮循环常常在定时器的下一个到期时间之后才结束，rcl 发现已经错过，就直接跳到再下一个周期。循环和 tick 之间的相位是好是坏，取决于很小的时序扰动：`rt_stats` 每 10 秒一次的打印把它推到了不好的状态。项目初期没有 `rt_stats` 时，`/odom` 也测到过一次 38 Hz、另一次 50 Hz。

**修复**：每轮等待改为 5 ms（`ros_config.h` 中的 `kSpinTimeoutMs`），定时器到期后最多一个 tick 内就能被处理。

| | 修复前 静止 / 运动 | 修复后 静止 / 运动 |
| --- | --- | --- |
| `/odom` 频率 | 34.1 / 39.1 Hz | 50.0 / 49.9 Hz |
| `/odom` 最大间隔 | 74 / 178 ms | 53 / 63 ms |
| `/imu` 频率 | 33.5 / 37.5 Hz | 49.0 / 48.1 Hz |
| `/scan` 频率（最大间隔） | 6.4 / 7.0 Hz（604 / 481 ms） | 9.1 / 9.2 Hz（314 / 301 ms） |
| `/battery_state`、`/ultrasonic` | 6.8 / 7.9 Hz | 10.0 / 10.0 Hz |
| `microros` CPU | 18.2 % | 28.2 % |

CPU 占用增加的比例和多发出去的消息（约 47%）差不多：每 1 Hz 发布量，修复前约占 0.53% CPU，修复后约 0.56%。所以缩短等待本身带来的额外开销很小。控制循环不受影响。

## 遗留问题

- **核负载不均衡**：可以把 `microros` 显式绑到 1 号核（`xTaskCreatePinnedToCore`），把它和 Wi-Fi、lwIP 分开。
- **`microros` 的栈太大**：缩小约 4 KB，可以还给堆，因为堆最低只剩过 36 KiB。
- **tick 配置不一致**：`sdkconfig.defaults` 写的是 `CONFIG_FREERTOS_HZ=1000`，而编译实际使用的 `sdkconfig` 是 100 Hz。删掉 `sdkconfig` 重新生成，tick 就会变成 1000 Hz，所有按 tick 计时的行为都会跟着变。需要二选一统一下来。
- `/imu` 修复后是 48–49 Hz，略低于 `/odom` 的 50 Hz，原因还没查。
- 这些数据都是在架空、静止加阶跃运动的情况下测的，没有覆盖雷达建图、多个 ROS 节点同时订阅等更重的负载。
